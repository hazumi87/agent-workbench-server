# Operator/developer exchange contract

Load when requesting or accepting a capability. Keep the message compact and link detailed reports.

## Developer response the operator needs

```text
Outcome: existing route / documentation fix / defect fix / new capability / blocked
Ready at: exact verb-doc section, revision and checkout availability
Run: one complete typed example on the stated input/copy
Effects: selections, units/space, sharing, dry-run writes, checkpoints and outputs
Tested: public entrypoint, fixture or real copy, input pin, saved-result checks
Limits: unsupported behaviour, approximation, untested scope, known defect
Operator acceptance: the one view or quantity resolving the request
Next owner: operator / developer / runtime / platform
```

Resolve ambiguous required fields, units, coordinate space, name/glob support, defaults, no-op behaviour and shared-material/mesh effects before running. A current developer handoff is authoritative for a newly supplied verb until the published list catches up. Do not edit the tool to compensate for missing docs.

The developer proves capability through the actual wrapper and downstream saved result. The operator proves the real asset's acceptance. Request a representative fixture, then a safe real-scene reproduction only when the failure depends on it. Avoid duplicating every normal modelling pass on both seats.

## Evidence scope

- Record original source hash separately from a re-saved copy and its output hash.
- Report measured counts, changed objects and images actually opened. Do not promote fixture-only results to full-scene guarantees.
- A sample, proxy ray, bound or centroid test retains its limits. Ask for corrected attribution when it conflicts with the actual file.
- A correction should identify what changed and what remains supported; replace the summary, do not leave contradictory headline claims.
- A code merge, checkout update, staged test, upload, served-file hash and real-device result are different milestones. Name the one actually reached.

## Context and ownership

Exchange the smallest source/job/args/error/reference/acceptance packet that reproduces the issue. Store traces, implementation history and fixtures in the developer record; model choices and reviewed artifacts in the operator record. Further evidence is pulled by topic, not by loading both histories.

For an infrastructure blocker, identify one owner and exact request. Include a proposed job name before workspace creation, current output destinations and existing authorization/holds. Don't treat HTTP reachability and process-table visibility as interchangeable evidence of service health. Don't restart a service from an operator diagnosis.

Example: cushion shoulders looked faceted. The operator compared shading on unchanged geometry; the developer found the wrapper overwrote the builder's shading flag. The resulting rule is end-to-end saved-result validation, not a mandate for denser meshes. Conversely, a strict UV coverage failure needs the exact exported UVs and loader rule, not an aesthetic rerender or a broad waiver.
