# Tool contracts and acceptance

The operator specifies the desired asset outcome. The developer supplies a supported operation,
typed settings and a reproducible test. A useful request contains the attempted verb/settings,
exact error or observed defect, protected inputs and an observable acceptance criterion.

Classify requests as an existing route, documentation ambiguity, reproducible defect, missing
capability or infrastructure blocker. Ask only for information that prevents reproduction or
acceptance. Keep private source assets outside the public repository; use synthetic fixtures
unless the fault genuinely requires an authorized private copy.

Test through the entrypoint the operator actually uses. Validate argument handling, affected
object counts, saved checkpoints and exports, not only a helper's in-memory result. Document
units, coordinate frames, selection semantics, defaults, dry-run writes and shared-data effects.

A developer fixture proves a capability within its tested scope. The operator still reviews the
real asset. Return one concrete invocation, the available revision, tested behavior, limitations
and the next acceptance check. Distinguish merged, installed, executed, visually reviewed,
published and deployed states.

Source changes and releases follow the current user's authorization. Prepare a concrete diff
before seeking any missing approval. Keep private project reproductions separate from public
synthetic test fixtures.
